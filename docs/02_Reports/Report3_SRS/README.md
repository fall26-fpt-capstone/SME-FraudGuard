Section 3 is a working specification of target behaviour, not implementation or test-execution evidence. Its 65 detailed functions cover UC-01 through UC-42. The 14 business groups run from Authentication and Account Access to Platform Monitoring and Audit. UI screen layouts are intentionally blank for later design; the overview still contains planned view descriptions, authorization, non-screen functions and logical relationships.

The current SRS sections 1, 2, 4 and 5 and later confirmed team decisions take precedence over superseded statements in `SOFTWARE_V1_BUSINESS_SPEC.md`. In particular, the current scope includes online Subscription purchase, Staff readiness -> Platform Admin approval -> SME Admin activation, and AI Normal/Anomaly without scores/confidence/explanations.

Confirmed detailed decisions include Open -> Investigating -> Pending Review -> Closed, with requests for additional work returning to Investigating. Conclusions are separate: Confirmed Fraud, Anomalous but Legitimate, False Alert, and Insufficient Evidence. SME Admin grants/revokes explicit field-view permission for Operator/Investigator without receiving plaintext access; Investigator also requires the relevant case assignment.

Account provisioning is controlled by the platform. Platform Admin creates the initial SME Admin and handles administrator replacement. Assigned Implementation Staff provisions Operator/Investigator accounts from enterprise-confirmed personnel requests, including additions after handover. SME Admin can change Operator/Investigator roles, immediately lock personnel access and administer field-view permissions, but cannot create accounts. Section 3's screen descriptions, authorization and member functions reflect this decision; existing role screen-flow images and the UC-09 actor catalogue still need synchronization, as do the native report, related Report 4/5 artifacts and historical dashboard references. Account quotas and seat billing are not introduced. Setup-token lifetime/resend/recovery, unlocking and administrator replacement safeguards remain separate design work.

Enterprise creation collects name, phone, enterprise email and a proposed subdomain, with live availability feedback and an authoritative uniqueness check at save. New enterprise recipients receive an FG-format username and an expiring, single-use password-setup link. Password setup precedes ordinary login and does not activate production. Specification discussions may happen externally; retain final agreed requirements and confirmation references. Protected uploads remain limited to the three authorized onboarding roles. These target changes are reflected in sections 3.2.2, 3.3.2 and 3.5.1; current backend text-only specifications and initial-password-change endpoints do not implement the complete invitation/upload flow.

Enterprise / Doanh nghiệp is the business-facing term; workspace remains the technical tenant scope. Backend enterprise login now accepts string `workspaceKey`; login/session responses expose UUID `workspaceId` and string `workspaceKey`. Existing clients need the new input and V5 deployment requires legacy-data preflight and enterprise re-login, as documented in the backend README. Implement independent, agreed API parts first; defer Webhook integration, rule configuration/testing and payment processing without deleting their target requirements. Catalogue CRUD is already implemented independently of payment.

Multiple Staff may be assigned concurrently. Configuration changes use a candidate draft, testing of the exact revision and explicit Staff application; stale edits/application are rejected. Accepted transactions retain their selected plan/configuration. Calendar Subscription periods use Asia/Ho_Chi_Minh, UTC storage and start-inclusive/expiry-exclusive validity. Recovery AI Anomaly creates/reuses one AI Alert per transaction; prior Rule Alerts, later Normal outcomes and existing cases retain their history.

Technical upload limits, exact Webhook/AI interfaces and credential settings belong to their confirmed interface/deployment specifications; illustrative fixture values are not global contracts.

Cloudinary is selected for protected uploaded-file storage, including retained onboarding documents. The application database retains workspace-scoped file metadata and asset references. Backend authorization governs upload and retrieval; sensitive files must not be publicly accessible. Temporary sample cleanup remains required. The native SRS Product Overview, section 3.5.1, External Interfaces, Security and Authorization, and CR-17 describe this separation. The business context diagram retains its existing system boundary; the Cloudinary integration is shown in the [Report 4 architecture](../Report4_SDD/sections/system-architecture.md).

Keep this source synchronized with scoped changes in the native document. The associated Report 4 data model is provisional. Report 5's UC-based designed tests are not proof of execution and still require detailed FR mapping after section 3 is finalized.
